## How it fits together (decisions already made — do not re-open)

```
Browser (portal)                 Portal server (Vercel)                    GitHub
 pdf.js reads PDF text    ──▶    POST /api/jobs   (text only, guards)
 job page polls + drives  ──▶    POST /api/jobs/:id/advance  one step per call:
                                   plan → [user reviews outline] → lecture 1..N → finish → publish
                                 uses vendor/core (copied from TEMPLATE/core)
                                   schema · widget catalogue · validator · generator  ──▶ repo from template,
                                                                                         content committed,
                                                                                         Actions builds Pages
```

1. **One source of truth.** `TEMPLATE/core/` holds schema, widget catalogue, validator and generator as pure TypeScript (imports: `zod` only; no `node:*`, no `react`, no `@/`). `PORTAL` holds a committed copy in `vendor/core/`, refreshed by a script.
2. **Text in, JSON out.** The browser extracts text per page. The server never receives a PDF. This removes P5, P7, P15 and makes any cheap or local model usable.
3. **The model writes JSON that is validated block by block.** Invalid blocks get one repair attempt, then are dropped. No reliance on a provider's schema feature.
4. **Jobs advance one step per request**, driven by the open job page. No step may exceed the function time limit. This removes P8–P10.
5. **The product is a template site.** `CourseRuntime` is deleted (P1, P12, P13). Until a GitHub token exists, a finished job offers a `course-bundle.json` download that `TEMPLATE` can import.
6. **Not in this iteration:** source figures, spaced repetition, gamification, interface translations, edit-by-chat, payments. They are the backlog at the end.

### Task C3: Plan, write, repair, finish

**Files:** `core/generate/prompts.ts`, `core/generate/plan.ts`, `core/generate/lecture.ts`, `core/generate/finish.ts`, `core/generate/lint.ts`, `core/generate/index.ts`, tests.

```ts
export interface PlannedLecture { number: number; slug: string; title: string; summary: string; pages: { file: string; from: number; to: number }[]; sections: { id: string; title: string; kind: SectionKind; blocks: string[] }[] }
export interface CoursePlan { course: Course; lectures: PlannedLecture[]; exam?: { title: string; intro: string } }
export const coursePlanSchema: z.ZodType<CoursePlan>
export async function planCourse(materials: Material[], brief: Brief, model: ModelClient): Promise<CoursePlan>
export async function writeLecture(plan: CoursePlan, index: number, materials: Material[], brief: Brief, model: ModelClient): Promise<{ lecture: LectureFile; dropped: Problem[] }>
export function lintLecture(lecture: LectureFile, brief: Brief): Problem[]
export function finishCourse(plan: CoursePlan, lectures: LectureFile[], brief: Brief): { files: Record<string, string>; problems: Problem[] }
export const DEFAULT_BUDGET = { inputTokens: 600_000, outputTokens: 120_000 }
```

**`planCourse`** — one call. The prompt gets all material text, the brief, and the rules: 1–12 lectures following the material's own structure; each lecture lists the page ranges it covers; every page with real content belongs to exactly one lecture; 4–8 sections per lecture, each with the block kinds it intends to use; `course.id` is a lower-case slug; `course.language` = brief language; `course.level`, `course.domains`, `course.theme.accent` (from the brief when given) filled in; `course.indexable` always `false`; `exam` present only when `brief.examMode`. After parsing: validate with `coursePlanSchema`, force `indexable: false`, clamp to `LIMITS.lectures`, renumber lectures 1..N, make slugs unique. One retry with the validation errors; then throw.

**`writeLecture`** — one main call with only that lecture's pages (`renderMaterials` with its ranges), the lecture's plan, the brief, the block reference (from `blockExamples`) and the widget catalogue (`generatorWidgetTypes`, each with description and example; omitted when `brief.widgets` is false). Rules in the prompt: use only facts from the given pages; write in the brief's language; every block carries `source` with the pages it came from; prose blocks ≤ 80 words; targets by depth — cram: 3+ concepts, 4+ quiz questions, 1 recall set; standard: 5+ concepts, 6+ quiz questions, 2 retrieval blocks, 1+ widget; deep: 8+ concepts, 8+ quiz questions, 3 retrieval blocks, 2+ widgets, 1+ worked example; quiz only when `brief.quizzes`.

Then, in code:
1. `extractJson`. Not JSON → one retry → throw.
2. Force `meta.number`, `meta.slug` from the plan. Validate `meta`, `concepts`, `quiz` items and each block **separately** (`validateBlock`). Collect invalid items with their problems.
3. If any are invalid: **one** repair call containing only the invalid items and their `formatProblem` lines, asking for corrected items in the same order. Re-validate; what still fails is dropped and returned in `dropped`.
4. Remove `concepts` block ids that no longer exist; remove sections left with no blocks; if no section is left, throw `Error("lecture produced no valid content")`.
5. `lintLecture`. If it returns warnings: **one** improvement call listing them, asking for additional blocks/questions only (same validation, steps 2–3 without another repair). Keep additions that are valid.

**`lintLecture` warnings:** `W301` fewer concepts than the depth target; `W302` fewer quiz questions than the target while quizzes are on; `W303` no `recall`/`practice` block; `W304` more than 60 % of blocks are `prose`; `W305` no `table`/`steps`/`timeline`/`widget`/`formula`/`code` block in the lecture; `W306` a block without `source`.

**`finishCourse`** — no model call. Returns `files`: `course.json`, `lectures/<NN>-<slug>.json`, and when the plan has `exam`: `exam.json` (lecture-shaped: `number: 0`, `slug: "exam"`, title and intro from the plan, one section with a prose block and a `mock-exam` widget, `quiz` = the first 3 questions of every lecture with ids prefixed `l<number>-`). Runs `validateCourseData` on the result and returns its problems; errors here are bugs in the generator.

**Tests (all with `fakeModel`):**
- plan: valid reply → plan with `indexable: false`; 14 lectures → clamped to 12 and renumbered; duplicate slugs made unique; invalid then valid → succeeds with exactly 2 calls; invalid twice → throws.
- lecture: all-valid reply → no repair call (1 or 2 calls depending on lint); a reply with one block of unknown kind and one widget with bad props → repair call receives exactly those two; unrepaired block is dropped and listed in `dropped`; a `concepts` block pointing at a dropped concept loses that id; a reply that is all invalid → throws.

**Files:** `lib/jobs/state.ts`, `lib/jobs/steps.ts`, `lib/jobs/claim.ts`, tests; delete `lib/gemini.ts`, `lib/job.ts` after their callers are gone.

```ts
export type Step = "plan" | "review" | `lecture:${number}` | "finish" | "publish" | "publish-wait" | "done"
export interface JobState { id: string; step: Step; status: "idle" | "working" | "awaiting-review" | "done" | "failed"; lecturesTotal: number; lecturesDone: number; attempts: number; error?: string; siteUrl?: string; bundleReady: boolean; usage: { inputTokens: number; outputTokens: number; calls: number }; createdAt: string; updatedAt: string }
export function nextStep(state: JobState, publishConfigured: boolean): Step           // pure
export async function claimStep(id: string, step: Step, attempt: number, now: Date): Promise<boolean>   // writes claims/<step>-<attempt>.json with overwrite disabled; false when it exists
export async function advance(id: string, deps: { model: ModelClient; now: () => Date; publish?: Publisher }): Promise<JobState>
```

Stored per job (through the existing `lib/storage.ts`): `state.json`, `brief.json`, `materials.json`, `plan.json`, `lectures/<n>.json`, `bundle.json`, `claims/*`.

`advance` rules: `awaiting-review`, `done`, `failed` → return the state unchanged. Otherwise claim `(step, attempts)`; if the claim exists and is younger than 330 s → return the state with `status: "working"`; if older → increase `attempts` (at 3 → `failed`, error "This step failed three times.") and return. With the claim: run exactly one step, save its output, move `step` forward, reset `attempts` to 0, add usage. Step `plan` ends in `status: "awaiting-review"`, `step: "review"`. Step `finish` writes `bundle.json`, deletes `materials.json`, sets `bundleReady`. When no publisher is configured, `finish` goes straight to `done`. A thrown error stores a short safe message (never a provider response body, never a key) and leaves the step to be retried. The per-job budget is `DEFAULT_BUDGET` minus `usage`.

Tests (fake model, in-memory storage adapter): happy path plan → review → lecture:1..N → finish → done; second `advance` during a fresh claim does not call the model; a stale claim increases `attempts`; three failures → `failed`; budget exhaustion → `failed` with "Generation budget reached."; `materials.json` is gone after `finish`.
